I read this as an architecture research deliverable - below is the cited technical report and an opinionated design matrix for a per-instructor Supabase application.

# Personal and long-term memory in AI agent systems

## Executive view

“Agent memory” is not one mechanism. Production systems generally combine four layers:

1. **Pinned instructions/profile**: small, trusted text or structured state injected into every prompt.
2. **Semantic memory**: durable facts and preferences retrieved by meaning.
3. **Episodic memory**: prior interactions or successful examples retrieved when relevant.
4. **Raw history/archive**: authoritative evidence retained outside the prompt for audit, reprocessing, and detailed retrieval.

The central engineering problem is therefore not storage but **controlled context construction**: deciding what to write, reconcile, retrieve, trust, and spend tokens on. LangMem uses the semantic/episodic/procedural taxonomy explicitly, while Letta distinguishes in-context memory blocks from searchable archival memory ([LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), [Letta stateful agents](https://docs.letta.com/v1-sdk/concepts/stateful-agents/), [Letta archival memory](https://docs.letta.com/v1-sdk/memory/archival-memory/)).

## 1. Agent-harness file memory

### 1.1 The common architecture

`CLAUDE.md`, `AGENTS.md`, and `.cursor/rules` are best understood as **filesystem-backed procedural memory**. The harness discovers trusted files by directory scope, resolves precedence, and inserts applicable text into the model context. They do not change model weights and usually do not perform vector retrieval; persistence comes from ordinary files, while “recall” comes from deterministic prompt assembly ([AGENTS.md specification](https://agents.md/), [Claude Code memory](https://code.claude.com/docs/en/memory), [Cursor rules](https://cursor.com/docs/rules), [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)).

This works unusually well because the memory is:

- **Transparent and editable**: humans can inspect and correct exactly what the agent sees.
- **Versionable**: project instructions participate in normal review, blame, branching, and rollback.
- **Portable**: standard Markdown can be consumed by several harnesses.
- **Deterministically scoped**: directory hierarchy provides a natural organization/project/package precedence model.
- **Already in the model’s native representation**: no schema-to-prose conversion is necessary before injection.

Those properties are explicitly reflected in AGENTS.md’s “README for agents” design, Cursor’s description of plain Markdown as the simpler alternative to structured rules, Claude’s editable instruction files, and Letta’s later git-backed MemFS design ([AGENTS.md](https://agents.md/), [Cursor rules: AGENTS.md](https://cursor.com/docs/rules#agentsmd), [Claude Code memory](https://code.claude.com/docs/en/memory), [Letta memory and dreaming](https://docs.letta.com/configuration/memory/)).

The weakness is that this is **prompt memory, not a database**. Every eagerly loaded instruction consumes context, contradictory prose may be applied inconsistently, and information buried in long prompts receives weaker attention. Claude recommends keeping each `CLAUDE.md` below roughly 200 lines; research on long contexts also shows “lost in the middle” degradation even when the text technically fits ([Claude Code memory](https://code.claude.com/docs/en/memory), [Lost in the Middle](https://arxiv.org/abs/2307.03172)).

### 1.2 Claude Code: `CLAUDE.md`, auto memory, and `/memory`

Claude Code currently distinguishes:

- **`CLAUDE.md`**: human-authored persistent instructions.
- **Auto memory**: Claude-authored notes derived from corrections, preferences, commands, and project learnings.

The documented instruction load order is broadest to most specific: managed organization policy, user instructions at `~/.claude/CLAUDE.md`, then project instructions such as `./CLAUDE.md` or `./.claude/CLAUDE.md`. Files above the working directory are loaded in full at launch; files beneath it are loaded on demand when Claude reads within those subdirectories. Project-local `CLAUDE.local.md` can hold uncommitted personal guidance ([Claude Code memory](https://code.claude.com/docs/en/memory)).

A `CLAUDE.md` can import another file with `@path`; imported content is expanded into startup context, including recursive imports up to four hops. Splitting a large file into imports improves maintainability but does **not** save prompt tokens unless the material is instead moved into path-scoped rules ([Claude Code memory](https://code.claude.com/docs/en/memory#import-additional-files)).

Auto memory is stored per project under Claude’s user configuration area, with a `MEMORY.md` entry point and optional supporting files. The first **200 lines or 25 KB** of auto memory are loaded each session; the agent’s memory facility can read and update those files, while `/memory` exposes the loaded memory locations for human review and editing. This is closer to self-maintained procedural/semantic notes than to raw transcript retrieval ([Claude Code memory](https://code.claude.com/docs/en/memory#auto-memory)).

Claude Code does not natively treat `AGENTS.md` as its instruction file; Anthropic recommends importing it from `CLAUDE.md` where a repository needs cross-harness compatibility ([Claude Code memory: AGENTS.md](https://code.claude.com/docs/en/memory#agents-md)).

### 1.3 Open `AGENTS.md` convention

The open convention imposes no required schema: it is standard Markdown, commonly containing setup commands, tests, conventions, and project-specific cautions. Nested files scope instructions to subprojects, the file closest to the edited code wins on conflict, and the explicit user request remains higher priority ([AGENTS.md](https://agents.md/)).

That specification is an interoperability convention rather than a guarantee that every product implements identical discovery. Exact traversal, byte limits, fallback names, and override behavior remain harness-specific ([AGENTS.md](https://agents.md/), [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Cursor rules](https://cursor.com/docs/rules#agentsmd)).

### 1.4 Codex `AGENTS.md`

Codex builds an instruction chain once per run:

1. At `CODEX_HOME`/`~/.codex`, it selects the first non-empty `AGENTS.override.md`, otherwise `AGENTS.md`.
2. From repository root to current working directory, it selects at most one file per directory in this order: `AGENTS.override.md`, `AGENTS.md`, then configured fallback names.
3. It concatenates root-to-leaf, so more local text appears later and overrides broader guidance.

The combined project-document default limit is **32 KiB**, configured by `project_doc_max_bytes`; empty files are skipped and loading stops at the cap. This is a concrete example of directory hierarchy acting as procedural-memory namespaces and precedence ([Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)).

### 1.5 Cursor rules and `AGENTS.md`

Cursor project rules are version-controlled `.mdc` files under `.cursor/rules`. Frontmatter controls applicability:

- `alwaysApply: true`: every chat.
- `globs`: attach for matching paths.
- `description` with non-always rule: expose the description so the agent can decide relevance.
- No automatic metadata: apply manually with an `@` mention.

A plain `.md` inside `.cursor/rules` is ignored because it lacks rule frontmatter; plain instructions should use `AGENTS.md` instead. Cursor supports nested `AGENTS.md` files and combines parent and child instructions, with the more specific child taking precedence. Across managed sources, Cursor documents precedence as **Team Rules → Project Rules → User Rules**, with earlier sources winning conflicts ([Cursor rules](https://cursor.com/docs/rules)).

**Architectural lesson:** file memory works best for a compact, high-confidence “core”: policies, stable preferences, commands, and workflows. It is a poor place for an unbounded interaction history or numerous uncertain facts because eager injection makes storage size equal recurring inference cost ([Claude Code memory](https://code.claude.com/docs/en/memory), [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)).

## 2. Letta / MemGPT

### 2.1 Virtual memory model

MemGPT framed the context window as limited main memory managed by an LLM “operating system,” with tools for moving information between in-context and external storage. Letta is the production evolution of MemGPT and persists agent state—including messages, reasoning, tool calls, and memories—even after material leaves the active context ([MemGPT paper](https://arxiv.org/abs/2310.08560), [Letta stateful agents](https://docs.letta.com/v1-sdk/concepts/stateful-agents/)).

### 2.2 Core memory as blocks

A Letta memory block is a labeled, described, character-limited text section prepended to the prompt in an XML-like representation. Attached blocks are always visible without retrieval; common labels include `persona` and `human`. Blocks are read-write by default, allowing the agent to revise its own persistent context through memory tools, but developers can mark them read-only. Blocks can also be shared across agents ([Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks/), [Letta stateful agents](https://docs.letta.com/v1-sdk/concepts/stateful-agents/)).

This makes self-editing memory explicit rather than incidental: the model can promote a durable preference into its `human` block, refine its persona, or reorganize a task-specific block. The advantage is immediate availability; the risks are prompt growth and destructive self-editing, so character limits, read-only blocks, and external version history matter ([Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks/)).

### 2.3 Archival memory

Archival memory is an external semantically searchable database for facts and knowledge. Its fragments cannot be pinned as blocks; the agent must search them on demand through tools. Letta recommends blocks for information that must always be visible or changes frequently, and archival memory for larger knowledge collections and older material ([Letta archival memory](https://docs.letta.com/v1-sdk/memory/archival-memory/)).

Thus “core versus archival” is a **latency/token versus capacity** trade-off:

| Property | Core block | Archival memory |
|---|---|---|
| Recall | Eager, every turn | Tool/search driven |
| Cost | Paid every prompt | Paid on retrieval |
| Capacity | Deliberately bounded | Large |
| Best use | Identity, current goals, stable preferences | Long-tail facts and historical material |
| Primary failure | Prompt bloat/stale pinned belief | Missed retrieval |

([Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks/), [Letta archival memory](https://docs.letta.com/v1-sdk/memory/archival-memory/))

### 2.4 Sleep-time compute

Letta’s sleep-time/dreaming design moves reflection off the interactive path. Background subagents review recent conversations, consolidate lessons, deduplicate or reorganize memory, and update persistent state without blocking active responses. The process may run after a configured number of messages or when context compaction occurs ([Letta memory and dreaming](https://docs.letta.com/configuration/memory/)).

This is architecturally important: memory formation can use a slower or more capable model and inspect a whole session rather than forcing extraction into every response. The cost is eventual consistency—new information may not be available immediately—and background writes still require provenance and conflict controls ([Letta memory and dreaming](https://docs.letta.com/configuration/memory/), [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).

## 3. mem0

### 3.1 Extraction and update pipeline

The published Mem0 architecture has two phases:

1. **Extraction**: process a recent user/assistant exchange together with recent messages and an asynchronously maintained conversation summary to produce candidate facts.
2. **Update**: retrieve semantically similar existing memories, then ask an LLM to select a mutation.

The mutation vocabulary is:

- `ADD`: no equivalent memory exists.
- `UPDATE`: enrich or revise an existing memory.
- `DELETE`: remove a memory contradicted by new information.
- `NOOP`: existing state already covers the candidate or no change is justified.

The LLM chooses the operation directly through function/tool calling rather than a separate fixed classifier ([Mem0 paper, architecture §2](https://arxiv.org/html/2504.19413#S2), [Mem0 repository](https://github.com/mem0ai/mem0)).

This is stronger than append-only “vector memory” because contradiction and duplication are write-path concerns, not left entirely to retrieval. It is still probabilistic: extraction can omit facts, similarity search can fail to surface the conflicting record, and an LLM can choose the wrong mutation. Production systems should therefore retain immutable source evidence and a mutation ledger rather than treating the current memory text as ground truth ([Mem0 paper](https://arxiv.org/html/2504.19413#S2.SS1), [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).

### 3.2 Graph variant

`Mem0^g` extracts entities and relationship triplets, resolves semantically similar entities, and uses LLM-based conflict detection when integrating new edges. Superseded relationships are marked invalid rather than physically removed, preserving history for temporal reasoning. The published implementation uses Neo4j alongside embeddings and LLM extraction ([Mem0 paper, graph memory §2.2](https://arxiv.org/html/2504.19413#S2.SS2)).

Graph memory helps when answers require joins or multi-hop relationships—such as an instructor’s course, institution, preferred rubric, and prior exception—but increases extraction calls, schema/entity-resolution complexity, latency, and operational surface. The Mem0 paper reports only about a two-percent overall judge-score improvement for the graph variant over base Mem0, so graphs are not automatically justified for ordinary profile retrieval ([Mem0 paper](https://arxiv.org/abs/2504.19413)).

### 3.3 Claims and criticism

The paper claims a **26% relative improvement** in LLM-as-judge score over its OpenAI-memory baseline, about **91% lower p95 latency**, and over **90% lower token cost** than full-context processing on its LoCoMo setup. These are author-reported results, not an independent audit ([Mem0 paper](https://arxiv.org/abs/2504.19413)).

Important caveats:

- The evaluation is built on LoCoMo’s hybrid human/LLM-generated conversations rather than live production traffic ([LoCoMo paper](https://arxiv.org/html/2402.17753#S8)).
- The Mem0 study excludes LoCoMo’s adversarial/unanswerable category because the required ground truths were unavailable, reducing coverage of abstention and poisoning-like behavior ([Mem0 paper, evaluation setup](https://arxiv.org/html/2504.19413#S3.SS1)).
- Lexical F1/BLEU can reward factually wrong answers with overlapping words, while LLM judges introduce model- and prompt-dependent variance; Mem0 therefore ran its judge multiple times, but this does not make the metric model-independent ([Mem0 paper, metrics](https://arxiv.org/html/2504.19413#S3.SS2)).
- Current repository headline results can refer to the managed platform and explicitly warn that proprietary optimizations are absent from the open-source SDK, so platform and OSS numbers should not be conflated ([Mem0 repository](https://github.com/mem0ai/mem0)).

The practical conclusion is to borrow the **extract → retrieve conflicts → mutate** pattern, but validate it on domain-specific conversations rather than selecting a vendor from headline LoCoMo scores.

## 4. Zep / Graphiti

Graphiti models memory as a temporal context graph containing:

- **Episodes**: raw ingested messages or records, retained as provenance.
- **Entities**: resolved people, objects, organizations, concepts, or events.
- **Facts/relationships**: entity-to-entity edges with validity intervals.
- **Communities/summaries**: higher-level graph organization.

It incrementally ingests structured and unstructured episodes and supports hybrid semantic, keyword, graph-traversal, and time-aware retrieval ([Graphiti repository](https://github.com/getzep/graphiti), [Graphiti overview](https://help.getzep.com/graphiti/getting-started/overview)).

### Bi-temporal validity

Graphiti/Zep distinguishes:

- **Valid time**: when the fact was true in the represented world.
- **Transaction time**: when the system learned or recorded it.

The Zep paper describes four edge timestamps corresponding to creation/expiration on those two timelines. This supports questions such as “What rubric did the instructor use last semester?” separately from “When did the system learn that the rubric changed?” ([Zep paper](https://arxiv.org/html/2501.13956#S2.SS1), [Graphiti overview](https://help.getzep.com/graphiti/getting-started/overview)).

When a new fact contradicts an existing relationship, Graphiti **invalidates the old edge rather than deleting it**. Entities generally remain reusable nodes; it is the time-bounded assertion edge that expires. Every derived fact remains connected to source episodes, allowing historical queries and provenance inspection ([Graphiti repository](https://github.com/getzep/graphiti), [Zep paper](https://arxiv.org/abs/2501.13956)).

This is a better model than overwriting a profile when historical correctness matters. It is heavier than needed for simple “current preferred tone” memory, and even Zep’s paper notes that existing memory benchmarks inadequately test synthesis between conversational and structured business data ([Zep paper, limitations](https://arxiv.org/html/2501.13956#S5)).

## 5. LangGraph and LangMem

### 5.1 Storage model

LangGraph separates:

- **Short-term/thread memory**: checkpointed graph state scoped to a conversation thread.
- **Long-term memory store**: records shared across threads and organized by tuple-like namespaces.

The `BaseStore` abstraction supports direct key access, writes/upserts, deletion, namespace listing, semantic search, and metadata filtering. A namespace such as `(organization_id, instructor_id, "preferences")` provides explicit tenant and subject isolation ([LangGraph memory concepts](https://langchain-ai.github.io/langgraph/concepts/memory/), [LangGraph store reference](https://langchain-ai.github.io/langgraph/reference/store/)).

LangMem layers extraction and reconciliation on top of the store. Store managers turn conversations into records and upsert/delete them; prompt optimizers treat procedural instructions themselves as improvable memory. Memory formation may occur in the hot path or in a background job ([LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).

### 5.2 Taxonomy

| Type | Meaning | Typical representation |
|---|---|---|
| **Semantic** | Facts and knowledge: “Instructor teaches BIO-201”; “prefers concise feedback” | Structured profile or searchable fact collection |
| **Episodic** | Past experiences and successful interaction examples | Retrieved conversation episodes/examples |
| **Procedural** | How the agent should behave | System instructions, policies, optimized prompts |

LangMem further distinguishes a **profile**—one schema-constrained current-state document—from a **collection** of individually searchable memories. Profiles are easy to display and edit but can overwrite nuance; collections preserve more detail but require dedupe, conflict resolution, and retrieval ranking ([LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).

## 6. RAG history, structured facts, and summary buffers

| Strategy | Retrieval quality | Cost/latency | Strongest use | Main failures |
|---|---|---|---|---|
| **RAG over raw history** | High fidelity if the correct turn is retrieved; weak on implicit preferences and multi-session synthesis | Embedding/index cost plus query/rerank latency; selected chunks consume substantial tokens | Quotes, exact events, provenance, re-answering from evidence | Chunk-boundary loss, semantic mismatch, duplicate hits, chronology errors |
| **Structured facts/profile** | High precision for known fields and current state | Cheap retrieval and compact injection; write path requires LLM/schema work | Stable preferences, role, course, goals, constraints | Extraction errors, schema rigidity, overwriting historical state |
| **Summary buffer** | Broad topical continuity with compact context | Repeated summarization cost; low read latency | Session continuity, recent goals, unresolved work | Irreversible detail loss, hallucinated synthesis, compounding drift |
| **Fact collection + vectors** | Good long-tail semantic recall with compact records | Moderate extraction and vector-search cost | Unbounded durable facts | Duplicates, stale contradictions, false semantic neighbors |
| **Temporal graph** | Strong for relationship joins and “true when?” questions | Highest ingestion and operational complexity | Dynamic entities, historical validity, multi-hop reasoning | Entity-resolution errors, expensive extraction, unnecessary complexity |

LongMemEval found that replacing source sessions with summaries or extracted facts can reduce QA performance through information loss, even though those representations save tokens. It also found that the optimal retrieved-token budget depends on reader capability and that perfect retrieval still does not eliminate reading/answer-generation errors ([LongMemEval paper](https://arxiv.org/html/2410.10813#S5)).

### Cross-cutting failure modes

- **Memory poisoning**: malicious or untrusted conversation text can be extracted as a durable fact or instruction and later retrieved into privileged prompts. Poisoned agent memory has been demonstrated as an attack surface, so retrieved memory must be treated as data, not authority ([AgentPoison](https://arxiv.org/abs/2407.12784)).
- **Stale facts**: append-only stores can return both old and current preferences. Validity intervals, explicit supersession, or current-profile reconciliation are required ([Graphiti repository](https://github.com/getzep/graphiti), [Mem0 paper](https://arxiv.org/html/2504.19413#S2.SS1)).
- **Over-personalization**: weakly inferred preferences may become self-reinforcing when repeatedly injected. Store assertion strength and distinguish explicit statements from inferred patterns; LangMem similarly notes that memory relevance should include importance and strength rather than similarity alone ([LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).
- **Prompt bloat**: eager memory competes with current instructions and conversation, reducing adherence. Claude’s under-200-line guidance and LongMemEval’s reader-budget results both support strict budgeting rather than “inject everything” ([Claude Code memory](https://code.claude.com/docs/en/memory), [LongMemEval](https://arxiv.org/html/2410.10813#S5)).
- **Provenance loss**: a compressed fact without its originating message cannot be audited or safely reinterpreted. Graphiti retains episode links specifically to preserve provenance ([Graphiti repository](https://github.com/getzep/graphiti)).

A robust system is therefore **hybrid**: current structured profile for always-needed state, semantic fact retrieval for long-tail memory, raw history as evidence, and a small recent summary for continuity.

## 7. Evaluation

### 7.1 LoCoMo

LoCoMo contains very long dialogues averaging about 300 turns and 9,000 tokens across as many as 35 sessions. Its tasks include single-hop, multi-hop, temporal, commonsense/world-knowledge, and adversarial QA, plus event summarization and multimodal dialogue generation. Conversations are generated from personas and temporal event graphs, then human-verified and edited ([LoCoMo paper](https://arxiv.org/html/2402.17753)).

It measures whether a system can retrieve and reason over long conversational evidence, but not whether production memory writes are privacy-safe, tenant-isolated, resistant to poisoning, inexpensive under load, or correct on a specific application’s schema. The authors acknowledge hybrid machine-generated data, limited multimodal exploration, English-only scope, reliance on closed models, and imperfect long-form generation evaluation ([LoCoMo limitations](https://arxiv.org/html/2402.17753#S8)).

### 7.2 LongMemEval

LongMemEval provides 500 questions covering information extraction, multi-session reasoning, temporal reasoning, knowledge updates, preference handling, and abstention. Its small configuration is roughly 115,000 tokens/40 sessions, while its larger form can contain around 500 sessions. It includes evidence-session and evidence-turn labels, enabling both final QA accuracy and retrieval Recall@k evaluation ([LongMemEval repository](https://github.com/xiaowu0162/LongMemEval), [LongMemEval paper](https://arxiv.org/abs/2410.10813)).

The benchmark’s strength is decomposition: it can reveal whether failure occurred during memory retrieval or later reading. It also includes knowledge-update and abstention questions that expose overwrite and hallucination behavior. Its GPT-4o correctness judge achieved high agreement with sampled human judgments, but open-ended preferences and abstention remain harder to judge consistently ([LongMemEval paper](https://arxiv.org/html/2410.10813#S3.SS3), [LongMemEval appendix](https://arxiv.org/html/2410.10813#A1.SS4)).

Its limitations are still substantial: questions are heavily curated, evidence sessions are LLM-simulated and human-edited, filler histories come from synthetic/public chat sources, and benchmark answers are mostly retrospective QA rather than proactive personalization. A 2025 cleaned release changed sessions to prevent irrelevant history from interfering with answer correctness, illustrating that benchmark construction itself materially affects scores ([LongMemEval repository](https://github.com/xiaowu0162/LongMemEval)).

### 7.3 What to measure in production

Benchmark QA accuracy should be supplemented with:

- extraction precision/recall by memory type;
- duplicate and contradiction rates;
- stale-fact retrieval rate;
- evidence/provenance correctness;
- retrieval Recall@k and answer accuracy conditional on oracle retrieval;
- p50/p95 write and read latency;
- tokens injected per response;
- per-session extraction cost;
- poisoning and cross-tenant leakage tests;
- user correction/deletion success;
- calibration: whether low-confidence memory is omitted.

The retrieval-versus-reader separation follows LongMemEval; latency and token accounting follow Mem0 and Zep’s production-oriented evaluations, while tenant/privacy controls are application requirements those benchmarks do not measure ([LongMemEval](https://arxiv.org/abs/2410.10813), [Mem0 paper](https://arxiv.org/abs/2504.19413), [Zep paper](https://arxiv.org/abs/2501.13956)).

## 8. Concrete engineering patterns

### 8.1 Write path

**Recommended default: session-end asynchronous extraction**, plus narrowly defined streaming triggers.

- Stream only explicit, high-value statements such as “Remember that…”, direct corrections, consent changes, or durable preference declarations.
- At session end, process the complete exchange into candidate facts, profile patches, episodic examples, and a session summary.
- Periodically run consolidation over recent candidates and existing active memories.
- Never block the user-facing response on ordinary extraction.

This combines LangMem’s hot-path/background distinction with Letta’s sleep-time consolidation and avoids adding an LLM call to every turn ([LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), [Letta memory and dreaming](https://docs.letta.com/configuration/memory/)).

### 8.2 Candidate record and provenance

Each memory should retain at least:

- tenant/application and instructor IDs;
- type: profile fact, semantic fact, episode, procedure;
- canonical predicate/category;
- normalized text and optional structured value;
- source session/message IDs and quoted evidence span;
- asserted-by role;
- explicit versus inferred status;
- confidence;
- valid-from/valid-to and recorded-at/superseded-at;
- embedding model/version;
- created/updated timestamps;
- mutation reason and extractor version.

This combines Graphiti’s episode provenance and bi-temporal model with the profile/collection distinction from LangMem ([Graphiti repository](https://github.com/getzep/graphiti), [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).

### 8.3 Dedupe and conflict resolution

1. Normalize the candidate into a domain predicate, such as `feedback_tone`, `course`, or `grading_policy`.
2. Retrieve active records for the same instructor and predicate using exact metadata first, then vector similarity.
3. Classify the relationship as duplicate, complementary, superseding, conflicting, or unrelated.
4. Apply `NOOP`, merge/update, add, or invalidate; never destroy source evidence.
5. Require user confirmation for sensitive or high-impact conflicts.

This is Mem0’s update vocabulary strengthened with Graphiti-style invalidation instead of irreversible deletion ([Mem0 paper](https://arxiv.org/html/2504.19413#S2.SS1), [Graphiti repository](https://github.com/getzep/graphiti)).

Use an idempotency key derived from instructor, source message, predicate, and extractor version so retries do not create duplicate facts. Use transactional updates or optimistic version checks when two background workers can reconcile the same profile concurrently.

### 8.4 TTL and decay

TTL should be semantic, not universal:

- Identity, accessibility requirements, and explicit stable preferences: no automatic expiry, but reviewable.
- Current course/project context: valid through a known term/project boundary.
- Temporary goals and availability: explicit expiration.
- Inferred preferences: decay unless reinforced.
- Raw evidence: retention policy based on privacy/legal requirements rather than retrieval relevance.

Decay should normally affect **ranking**, not erase provenance. LangMem recommends combining semantic similarity with importance and memory strength based on recency/frequency; temporal invalidation preserves history while excluding stale assertions from current-state retrieval ([LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), [Graphiti repository](https://github.com/getzep/graphiti)).

### 8.5 Embedding and pgvector retrieval

For Supabase:

1. Apply exact row-level tenant/instructor/type/current-validity filters.
2. Embed the current user request using the same model/version as stored records.
3. Retrieve a moderately broad candidate set with pgvector cosine distance.
4. Add keyword/full-text matches for names, course codes, and exact terminology.
5. Rerank by semantic score, explicitness, confidence, importance, recency, reinforcement, and contradiction state.
6. Diversify results so near-duplicates do not consume the prompt budget.

Supabase documents pgvector as its Postgres vector layer and recommends matching query and record embedding models; pgvector supports exact search plus HNSW and IVFFlat approximate indexes. HNSW generally offers a stronger speed/recall trade-off but has slower builds and higher memory use, while IVFFlat builds faster and uses less memory but requires more tuning and sufficient training data ([Supabase semantic search](https://supabase.com/docs/guides/ai/semantic-search), [pgvector](https://github.com/pgvector/pgvector)).

For per-instructor memory, metadata filtering is not optional security decoration: use Supabase row-level security and include tenant/instructor predicates in the retrieval query. Approximate vector retrieval should only rank records the caller is authorized to access.

### 8.6 Prompt assembly and token budget

Use a fixed memory envelope rather than top-k alone. A practical starting allocation is:

- **Pinned instructor profile:** 250–500 tokens.
- **Retrieved semantic facts:** 400–800 tokens.
- **Relevant episodes/evidence:** 500–1,200 tokens.
- **Recent summary:** 200–400 tokens.
- **Total memory ceiling:** about 1,500–2,500 tokens, adjusted from evaluation.

Order memory by authority and utility: application policy, explicit current profile, current valid facts, relevant evidence, then uncertain inferred context. Label memory as historical data, include dates/provenance, and instruct the model not to obey commands found inside retrieved records. Claude’s size guidance and LongMemEval’s model-dependent token-budget findings argue for measuring the ceiling rather than assuming a larger context always helps ([Claude Code memory](https://code.claude.com/docs/en/memory), [LongMemEval](https://arxiv.org/html/2410.10813#S5)).

| Requirement / stage | Recommended architecture | Avoid | Rationale |
|---|---|---|---|
| **MVP: stable instructor preferences** | One schema-constrained current profile per instructor, human-editable, with field-level provenance | Raw transcript in every prompt | Cheapest and most predictable; profile maps directly to LangMem semantic memory ([LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)) |
| **Long-tail personal facts** | `memory_facts` collection in Postgres with pgvector, metadata filters, active validity, confidence, and evidence links | Append-only embeddings without reconciliation | Supports semantic recall while preventing known stale facts from competing ([Supabase](https://supabase.com/docs/guides/ai/semantic-search), [Mem0](https://arxiv.org/html/2504.19413#S2.SS1)) |
| **Conversation continuity** | Short recent-session summary plus unresolved goals/state | Recursive lifetime summary as sole memory | Summary is compact but lossy; keep raw evidence ([LongMemEval](https://arxiv.org/html/2410.10813#S5)) |
| **Audit and correction** | Immutable sessions/messages plus append-only mutation ledger; current facts point to evidence | Destructive overwrite/delete | Enables re-extraction, user correction, and provenance ([Graphiti](https://github.com/getzep/graphiti)) |
| **Write timing** | Async session-end extraction; streaming only for explicit remember/correction events | LLM extraction synchronously after every turn | Lower response latency and better session-level context ([LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), [Letta](https://docs.letta.com/configuration/memory/)) |
| **Conflict handling** | Predicate-aware `ADD/MERGE/SUPERSEDE/NOOP`; invalidate old fact with validity dates | Physical deletion of contradicted facts | Combines Mem0 reconciliation with temporal history ([Mem0](https://arxiv.org/html/2504.19413#S2.SS1), [Graphiti](https://github.com/getzep/graphiti)) |
| **Retrieval** | Exact scope/current filters → vector + full-text candidates → application reranking → token-budget packing | Pure global nearest-neighbor top-k | Names/codes need lexical matching; similarity alone ignores authority and staleness ([Supabase](https://supabase.com/docs/guides/ai/hybrid-search), [LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)) |
| **Index** | Exact search initially; HNSW once corpus/latency warrants it | Premature graph database or IVFFlat tuning on tiny data | pgvector exact search is simplest at small scale; HNSW is available later ([pgvector](https://github.com/pgvector/pgvector)) |
| **Prompt injection** | Treat retrieved memory as quoted data, strip executable authority, show provenance, exclude low-confidence inference | Putting retrieved text inside the authoritative system-policy section | Persistent stores are poisoning targets ([AgentPoison](https://arxiv.org/abs/2407.12784)) |
| **Temporal questions** | Add `valid_from`, `valid_to`, `recorded_at`, `superseded_at` to facts | Only `updated_at` | Minimal relational implementation of bi-temporal semantics ([Zep paper](https://arxiv.org/abs/2501.13956)) |
| **Knowledge graph** | Defer until real queries require multi-hop relationships or historical graph traversal | Graphiti/Neo4j as the initial profile store | Mem0 reports only a modest overall graph uplift, while complexity rises materially ([Mem0](https://arxiv.org/abs/2504.19413)) |
| **Evaluation** | Build an instructor-specific set of explicit preference, update, contradiction, abstention, temporal, and poisoning cases | Choosing architecture from vendor LoCoMo rankings alone | Public benchmarks omit tenant security and domain behavior ([LoCoMo](https://arxiv.org/html/2402.17753#S8), [LongMemEval](https://arxiv.org/abs/2410.10813)) |

## Opinionated target architecture

For this application, use **Postgres as the source of truth and pgvector as one retrieval index—not as the memory model itself**:

1. Immutable `sessions/messages` retain raw evidence.
2. A versioned `instructor_profile` stores compact, explicit current state.
3. A temporal `memory_facts` collection stores durable long-tail assertions with provenance and embeddings.
4. Optional `memory_episodes` store only useful prior examples, not every arbitrary exchange.
5. Session-end background jobs extract candidates and reconcile them transactionally.
6. Prompt assembly always includes the small profile, retrieves facts/episodes under an explicit token budget, and labels all retrieved content as untrusted historical data.
7. A user-facing memory editor allows instructors to inspect, correct, pin, or forget memories.

Do **not** begin with Graphiti, full-history RAG, or a managed memory vendor. The profile-plus-temporal-facts design captures most of the practical value of Letta, Mem0, LangMem, and Graphiti while remaining native to Supabase, auditable, tenant-safe, and reversible. Add a graph only after production query logs demonstrate that relational multi-hop retrieval—not extraction quality, stale facts, or prompt assembly—is the actual bottleneck.
